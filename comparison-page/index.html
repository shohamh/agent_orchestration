Self-hosted agent orchestration · offline network evaluation

Hatchet vs Prefect vs Trigger.dev

All three ran side by side with Docker Compose on one machine, each with the same agent examples. The comparison covers three requirements: agents bound to local hardware, agents a human can interrupt and steer, and trace collection.

Hatchet v0.114.2Prefect 3.9.1Trigger.dev v4.8.3Tested 2 Nov 2026Docker Compose, single host

Verdict

1 · Prefect 1 · Hatchet 3 · Trigger.dev

Prefect and Hatchet are both strong fits for agents in an offline network that talk to local hardware and need human steering. Startup time and keeping a process alive during human waits are acceptable for this use case. Choose Prefect for Python workflows, its run graph and built-in approval forms. Choose Hatchet for durable recovery after worker restarts, multiple worker languages and its integrated trace viewer. Trigger.dev suits TypeScript web-facing agents that never touch local devices.

  • Hardware: Hatchet and Prefect run agent code as ordinary processes on the PC with the device, and both route work to a specific PC. Trigger.dev's self-hosted Docker worker runs each run in a container with no device access.
  • Steering: all three passed redirect, stop and cancel tests. Hatchet's waits survive restarts and release the worker. Prefect renders typed approval forms in its UI, but polls for messages. On self-hosted Trigger.dev, a waiting run holds its container.
  • Traces: Hatchet and Trigger.dev show traces in their own dashboards. Prefect creates spans but has no viewer, so it needs an OTLP backend. All three were verified in a shared Jaeger.

Requirement 1

Agents that talk to hardware on their own PC

HatchetNatural fit

A worker runs on each PC that has the device, natively or in Docker with devices:. Labels such as device=sensor route the task there, and a caller can pin a run to one station. slots=1 serializes device access.

Tested: ran only on labelled workers; per-run pin landed on station-a.
PrefectNatural fit

A process worker on each PC polls a work pool. Each PC has its own queue, plus a shared any-station queue. Runs are local subprocesses with full host access. run_deployment(..., work_queue_name=…) pins a run, and --limit 1 serializes access.

Tested: unpinned runs went to a free station; pins landed on a and b.
Trigger.devIndirect

Regions can send a run to a machine, but it executes in a container that gets only network, CPU and memory settings. It has no devices, volumes or privileged mode. You need a bridge service on each PC, a patched supervisor, or development mode.

From source: apps/supervisor/src/workloadManager/docker.ts
Requirement 2

Human-interruptible and steerable agents

HatchetStrongest durability

Between steps the agent durably waits for a timeout or a steer event scoped to its run. Cancel works from the dashboard or API. Waits survive worker restarts, and the worker slot is released while waiting. You build any approval form yourself.

Tested: redirect, graceful stop, cancel → CANCELLED.
PrefectBest human input UX

send_input / receive_input steer a running flow. pause_flow_run(wait_for_input=Model) shows a typed form with a Resume button in the UI. Messages are polled. A paused flow keeps its process alive, which is acceptable here. A suspended flow frees it, but re-runs from the start on resume; result reuse requires explicit task caching.

Tested: redirect, stop, cancel → CANCELLED, pause and resume with input.
Trigger.devMost UI-ready

Input streams (steer.send / steer.once), waitpoint tokens, live metadata, realtime streams and AI-chat helpers. Self-hosted has no checkpoints, so long human waits keep the run's container running.

Tested: redirect, graceful stop, cancel → CANCELED.

Found while setting up

Setup findings

  • Prefect: unknown work queue = silent idle workerA worker started with a queue that doesn't exist picked up no runs at all, not even from its other queues, and logged no error. Create queues before starting workers.
  • Prefect: results across machinesTo read a run's result from another process, results must be persisted to storage every worker can reach.
  • Trigger.dev: runs call the API from inside containersWith a localhost public URL, child tasks and steering fail. The fix is INTERNAL_API_ORIGIN and STREAM_ORIGIN pointing at the internal webapp, or a real DNS name.
  • Trigger.dev: offline deploys have hidden downloadsThe build needs digest-pinned base images, a Dockerfile syntax image and an npm registry. All three are mirrored by the offline bundle.
  • Hatchet: trace collector is off by defaultSet SERVER_OBSERVABILITY_ENABLED=true on the engine, or workers silently drop their spans.
  • Hatchet: REST calls from containersTokens embed the public URL. Inside Docker, set HATCHET_CLIENT_SERVER_URL to the internal address.

Rows marked tested were run against the local setup with the example code (task, fan-out pipeline, agent loop, steerable agent, approval, hardware-bound task). Other rows come from the official documentation and the SDK and server source at the listed versions. All three are in the offline bundle.
