Self-hosted agent orchestration · offline network evaluation

Hatchet vs Trigger.dev

Both tools ran side by side with Docker Compose on one machine, using the same agent examples. This page covers three requirements: agents bound to local hardware, agents a human can interrupt and steer, and trace collection.

Hatchet v0.114.2Trigger.dev v4.8.3Tested 2 Nov 2026Docker Compose, single host

Verdict

Hatchet is the better fit for agents in an offline network that must talk to hardware on the PC they run on. That holds especially if any agent code is Python. Trigger.dev suits TypeScript-first teams building web-facing agents that stream to a UI, where per-run isolation and versioned deploys matter more than hardware access.

  • Hardware: Hatchet workers are your own processes, so they reach any device the PC exposes. Labels route each task to the right machine. Trigger.dev's self-hosted Docker worker runs every run in a fresh container with no device or volume passthrough.
  • Steering and interrupts: both work, and both were tested here: redirect mid-run, graceful stop, hard cancel. Hatchet's waits are durable and free a worker slot. On self-hosted Trigger.dev, a waiting run keeps its container alive.
  • Traces: both collect per-run traces in their own dashboards, and both export to a shared OTLP backend. Both were verified in Jaeger.
  • Running offline: Hatchet only needs docker save and docker load. Trigger.dev also needs mirrored build base images, an npm mirror and a host-network builder. All of it is scripted and was tested.

Requirement 1

Agents that talk to hardware on their own PC

HatchetNatural fit

Run a worker on each PC that has a device, natively or in Docker with devices:. It advertises labels such as device=sensor and station=lab-pc-2. Tasks declare the labels they need, and a caller can pin a run to one station. slots=1 serializes access to the device.

Tested: read-sensor ran only on labelled workers, and the per-run pin landed on station-a.
Trigger.devIndirect

Regions (worker groups) can send a run to a specific machine, but the run executes in a container the supervisor creates with only network, CPU and memory settings. It has no devices, volumes or privileged mode. To reach hardware you need a small bridge service on each PC that tasks call over HTTP, a patched supervisor, or trigger dev on that PC (development mode only).

From source: apps/supervisor/src/workloadManager/docker.ts
Requirement 2

Human-interruptible and steerable agents

HatchetStrong

Between steps, the agent durably waits for either a short timeout or a steer event scoped to its run. A human pushes agent:steer with a new instruction or a stop. A hard interrupt is a normal cancel from the dashboard or API. Waits survive worker restarts, and the worker slot is released while waiting.

Tested: goal redirected mid-run, graceful stop, cancel → CANCELLED.
Trigger.devStrong

Input streams: steer.send(runId, …) from outside, and steer.once(), .on() or .wait() inside the task. Waitpoint tokens handle approvals, and cancel works from the dashboard or API. Live metadata and realtime streams make a UI easy, and there are AI-chat helpers with steering. Self-hosted has no checkpoints, so long human waits keep the run's container running.

Tested: redirect, graceful stop, cancel → CANCELED.

Self-hosted Trigger.dev needed STREAM_ORIGIN pointed at the internal webapp address. Without it, steering messages are stored but never reach the run. This was found during testing and is fixed in the setup.

Found while setting up

Setup findings

  • Trigger.dev: runs call the API from inside containersWith the public URL on localhost, child tasks and steering fail. The fix is INTERNAL_API_ORIGIN and STREAM_ORIGIN pointing at the internal webapp, or a real DNS name for the server.
  • Trigger.dev: offline deploys have hidden downloadsThe build pulls digest-pinned base images, a Dockerfile syntax image from Docker Hub, and runs npm install inside the image. The offline bundle mirrors all three. A deploy was verified using only the local registry and an offline npm mirror.
  • Trigger.dev: parallel child waitsPromise.all over triggerAndWait fails. Use batch.triggerByTaskAndWait.
  • Hatchet: trace collector is off by defaultSet SERVER_OBSERVABILITY_ENABLED=true on the engine, or workers silently drop their spans.
  • Hatchet: REST calls from containersAPI tokens embed the public URL. Inside Docker, set HATCHET_CLIENT_SERVER_URL to the internal dashboard address.
