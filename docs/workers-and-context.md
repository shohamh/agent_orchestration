# Execution workers and environment setup

Steps run on registered PCs, including the one the flow host runs on: there is no built-in Fleet
execution PC. Selected Hatchet work is executed by a Hatchet SDK worker on the registered PC;
selected Prefect work is executed by that PC's process worker in its configured pool/queue.
Trigger.dev remains a shared Fleet relay bridge, and its deployed workers remain isolated
containers. Native Hatchet/Prefect and relay-dispatched work share the per-PC capacity gate.
Engine-launched flows without an explicit selection use a compatible fleet worker. Standalone
sessions with an existing workspace or resume ID retain their local executor behavior.

Each engine keeps its native orchestration. The board reports the actual execution worker, hostname,
pool and tags after admission. A worker is not considered ready until its selected native engine
worker is ready. Engine endpoint reachability, cross-PC native transfer/cancellation and combined
native/relay admission are not verified here.

## Register a PC

One registration is one PC, however many engines and pools it serves. In the board, open
**Fleet**, then **Register PC**. Registering is a short form plus one command:

1. **Fill in the form.** Name, the PC's operating system, the engines it serves, a pool (or a new
   one), optional tags, slots and CPU/RAM limits (defaults 1, 90% and 90%), the address the PC uses
   to reach this server (pre-filled from the page; it cannot be `localhost`), and its startup and
   restart choices. When Hatchet is selected, provide a dedicated worker-capable Hatchet token for
   this PC; do not use the Board-global token. Nothing is created until every field is valid.
2. **Copy the command.** The server generates a UUID for this install and shows one command per
   shell. It downloads `agent-worker` and runs `agent-worker install <uuid> --server <address>`.
   The token is never placed in the command:
   - Windows PowerShell: `$f = Join-Path $env:TEMP 'agent-worker.exe'; iwr -UseBasicParsing 'http://<server>/install/<uuid>/agent-worker' -OutFile $f; & $f install <uuid> --server 'http://<server>'`
   - Windows Command Prompt: the same with `curl.exe`
   - Linux: `f=$(mktemp) && curl -fsSL '…/agent-worker' -o "$f" && chmod +x "$f" && "$f" install <uuid> --server 'http://<server>'`

   **Run it as a normal user. Do not use Administrator or sudo.** Everything installs for that
   user, and nothing on the PC is opened to the network.
3. **Watch it connect.** The page shows each step and the reason for any failed step. A failed native
   runtime setup must not leave a worker registered as ready; installation rolls back its partial
   native setup. Closing the tab does not lose the install: it stays listed under "Waiting to be
   installed" with **Show command** and **Cancel**.

The install UUID is the only secret-like value in the command. On the valid PC claim, the server
delivers the dedicated Hatchet token only in that claim response; it is not returned in install
views, worker status or logs. It is stored in a separately protected local secret file for the
native Hatchet component, never in generic worker configuration. It is never sent for an invalid
claim or a different PC. Cancel invalidates that UUID for both downloads and claims.

### Unregistering a worker

In **Fleet**, choose **Unregister** on the worker card or **Unregister from Fleet** in its
context menu, then confirm the removal. The server removes the registration, closes its old install
record and revokes its relay authorization and engine routing. Unregister must be safe to repeat.
The local installation remains and must not accept new work; cancellation/fencing of work already
running is not synchronous and remains unverified for native engine paths. A new install link is
required to restore the PC and replaces the local worker identity in place.

Opening the binary download URL in a browser supplies the platform's release filename:
`agent-worker-x86_64-pc-windows-msvc.exe` on Windows or
`agent-worker-x86_64-unknown-linux-musl` on Linux. The board preserves this filename when proxying
the download; the original `/install/<uuid>/agent-worker` URL does not need an `.exe` suffix.

### Identity: a name and a uuid

Every worker has a **name**, chosen in the form and unique (flow selectors use it), and a **uuid**,
generated by the server for that install and never chosen by anyone. The uuid keys the relay and the
registry and cannot change. It is also what stops one command being run on two PCs: the first PC to
run `install <uuid>` stores the hash of a secret it generated and the OS and host name it reported;
a second PC presenting the same uuid is refused with a message naming the first host and the time.
An operating system that differs from the one in the form is refused too.

### What `agent-worker install <uuid>` does

1. Contacts the server (`POST /install/<uuid>/claim`) before changing an existing local install.
   The claim is bound to that PC identity; only a valid claim receives its dedicated Hatchet token,
   and only when Hatchet was selected. The server refuses a duplicate live registration; unregister
   it in Fleet before creating a replacement.
2. Receives the saved worker settings and, when selected, the Hatchet token in the protected claim
   response. The token is written to a separately protected local file, not generic worker
   configuration, status, logs or the install command.
3. Installs or updates the bundled native runtime and selected engine components. The release and
   offline-load paths include Windows and Linux native-runtime archives with CPython and the
   Hatchet/Prefect SDK dependencies; the Rust installer downloads the selected archive, checks its
   version digest and starts the selected components before reporting readiness. A Windows archive
   build succeeded in local verification. The Linux archive could not be verified here because
   the upstream CPython download returned HTTP 504 on all bounded retries. Native engine runtime
   packaging does not currently target macOS. Offline rollout needs both platform archives present
   in the server's `dist/worker` directory.
4. Starts the Hatchet SDK worker on this PC when Hatchet is selected. For Prefect, creates the
   configured process work pool if absent, reuses it if present, and runs a process worker polling
   the configured queue. Compatible routed work executes in those PC-native workers. Trigger.dev
   remains a shared Fleet relay bridge; its deployed workers remain isolated containers.
5. Completes Fleet registration only after native engine readiness. The worker stays registered
   with the same identity during an update.

The `agent-worker` executable is static and needs no Python. The native runtime archives and offline
per-OS engine dependencies are bundle prerequisites, not assumed system packages. Other components,
such as ACP adapters, may still need Node.js/npm or access to the bundled server mirror. Real agents
also need their CLI and model credentials/configuration. The built-in `demo` agent requires no model.

### When the worker starts: logon, boot or never

The form asks, and the PC applies it during `agent-worker install`. The page explains the consequences next to each choice.

| Choice | What happens | Consequence |
|---|---|---|
| **When the user logs in** (default) | Windows: a Scheduled Task with a logon trigger, running as that user with their environment. Linux: a `systemd --user` unit. Needs no administrator rights. | After the PC restarts the worker is not running until someone logs in, so the PC shows offline in the fleet until then. Tools and agents that depend on the user's login, credentials and PATH work. |
| **When the PC starts, before anyone logs in** | Windows: the same task also gets a boot trigger and runs as the user without a stored password (S4U). Linux: `loginctl enable-linger`. | It runs without the user's credentials: no saved Windows or network logins, mapped drives, desktop or logged-in sessions, and not the user's logon environment (the install recorded the PATH and profile folders it saw and the worker restores them). Agents and tools that need the user to be signed in can fail until the user logs in. |
| **Do not start automatically** | No startup entry; the worker runs now as a background process. | After a restart it stays off, offline in the fleet, until `agent-worker start`. |

Everything works as a normal user, without administrator rights. Starting at boot is the one step that
needs them, because a boot trigger is machine-wide: **Windows shows a UAC prompt** (during the install, or
when you run `agent-worker boot enable` in a normal shell), the program re-runs only that step elevated, and
everything else stays the user's. If the prompt is declined, or the elevated prompt was answered with a
different administrator account, the worker starts at logon instead and says why; `agent-worker boot enable`
tries again later. On Linux the step runs `loginctl enable-linger` and prints the exact `sudo` command if it is not allowed.
Lingering is a setting of the user, not of one worker.

### Restarting after a crash: on or off

The form has a checkbox, on by default: **restart automatically if the worker crashes or is killed**. Turn it off to
leave a stopped worker down, for example while you debug it. It only applies when the worker starts by itself (logon or boot);
without a startup entry nothing restarts it anyway.

| | On | Off |
|---|---|---|
| Windows | the task re-runs every minute and starts the worker if it is not running (a crash costs up to a minute), and Task Scheduler restarts it on failure | the task only has its logon (and boot) trigger: a killed worker stays down until the next logon or start-up, or `agent-worker start` |
| Linux | `Restart=always`, 5 seconds | `Restart=no` |
| Components | restarted with a growing delay | a component that exits stays down (state `exited`) until `agent-worker restart NAME` |

Change it later on the PC with `agent-worker autorestart on|off|status`. On Windows a task that starts at boot is rebuilt through the
UAC prompt like `boot enable`; if the prompt is declined nothing changes and the setting is put back.

### How it starts, restarts and stops

| | Windows | Linux |
|---|---|---|
| Service | Scheduled Task `AgentWorker-<name>` | `systemd --user` unit `agent-worker-<name>.service` |
| After a crash or kill (auto restart on) | the task re-runs every minute and starts the worker if it is not running (at most a minute), plus Task Scheduler's own restart on failure | `Restart=always`, 5 seconds |
| `agent-worker stop` | disables the task and leaves a marker so a check that still runs does nothing; `start` undoes both | stops it until the next login or `start` |
| Limits | no time limit, runs on battery | none |
| macOS | LaunchAgent (`KeepAlive`) | |

A second copy never runs: `run` exits if a worker is already alive for the folder. The Task Scheduler is asked
whether the task is running, because a worker started at boot lives in a session the user's shell cannot always inspect.
`AGENT_WORKER_SERVICE=process` forces the plain background process (used by the tests; no startup entry is created) and
`AGENT_WORKER_NO_ELEVATE=1` makes `boot enable` refuse instead of showing a UAC prompt.

Tested on both systems with the real program, not mocks: install by uuid, each of the three start choices, the second install
refused, the startup entry created and removed, the worker killed with `kill -9` / `taskkill /F` and brought back, a stopped
worker staying stopped past the next check, and a fleet update through the service manager (the updater is started outside the
service so that stopping the service does not stop it). On Windows the boot step was run through a real UAC prompt, and
`status`, `stop`, `start`, `restart` and `uninstall` then worked from a normal shell on the boot task. Not exercised: an actual
reboot to the logon screen. Run the tests with
`AGENT_WORKER_SERVICE_TESTS=1 python -m unittest agents.tests.test_agent_worker_cli`
(the service tests create a real Scheduled Task or systemd user unit for the current user and remove it again; they never raise a UAC prompt).

### Managing a worker: `agent-worker`

| Command | What it does |
|---|---|
| `agent-worker status [--json]` | Service, local health, connection to the server, version, components |
| `agent-worker start`, `stop`, `restart [NAME]` | The worker and its components, or one component |
| `agent-worker boot [enable\|disable\|status]` | Choose when the worker starts after the form's choice: with the PC (even at the Windows logon screen), at logon, or see which. On Windows `enable` and `disable` ask for administrator approval through the UAC prompt |
| `agent-worker autorestart [on\|off\|status]` | Restart the worker when it crashes or is killed, or leave it down. Windows boot tasks ask for UAC approval to change |
| `agent-worker logs` | The worker log |
| `agent-worker update` | Fetches the version the server serves, waits for running jobs (drain), swaps the program, restarts, and goes back to the previous one if the new one does not come up |
| `agent-worker uninstall [--yes] [--keep-registration]` | Stops and removes the service, deregisters from the server and deletes the install folder |
| `agent-worker component list`, `add`, `remove` | Other processes the worker supervises (an engine worker, or your own service that manages it), restarted with backoff and controlled the same way |
| `agent-worker version` | A 16-character version: the start of the SHA-256 of the program |

### Updating the fleet

In the board, **Fleet → Update workers** shows the version each PC runs and its state. **Update all
workers now** makes the server's current program the target for each operating system. A connected
PC is told to update and does it itself (drain, swap, restart, roll back on failure). A PC that is
down updates when it next connects, and **Get update command** gives a one-time command for it (an
`agent-worker update --server … --code … --force` that downloads the new program and installs it
over the old one). Put the new programs in `dist/worker/` (see below) before pressing the button.
Automatic requests are limited to three attempts per target version, at least ten minutes apart.
The first request is immediate even just after boot; selecting a different target resets that
version's retry budget.

An update link uses its own one-time authorization token, not the install or worker uuid. Its
`/update/<token>/agent-worker` download and completion request pass through the board without an
interactive board login; the relay still validates the token and its expiry. Once the update is
reported complete or failed, that link cannot download again. Normal Fleet management APIs
continue to require board login. Browser downloads retain the same platform filename as installs.

### Building and releasing the worker

`worker/` is a Rust crate. `worker/ci/build.sh` (Linux, static musl) and `worker/ci/build.ps1`
(Windows, static C runtime) write `agent-worker-x86_64-unknown-linux-musl` and
`agent-worker-x86_64-pc-windows-msvc.exe`, each with a `.sha256`, into `dist/worker/`, which the
server serves. Pushing a tag `worker-vX.Y.Z` runs the same scripts in **GitHub Actions**
(`.github/workflows/worker-release.yml`) and in **GitLab CI** (`.gitlab-ci.yml`), which publish a
release with both programs. `worker/ci/fetch-release.sh` downloads the assets of a release into
`dist/worker/` for an offline server. The Rust dependencies are vendored in `worker/vendor/` (pruned of import libraries for Windows targets we do not build), so
`cargo build --locked` needs no network; `worker/ci/vendor.sh` refreshes them after a `Cargo.toml` change.

Windows release EXEs are Authenticode-signed using a free self-signed `CN=Agent Orchestration`
certificate. The signature identifies the signer by certificate thumbprint, but a self-signed
certificate does not establish a publicly trusted publisher or SmartScreen reputation and does not
guarantee a Defender verdict. The Windows `.sha256` file and release `SHA256SUMS` are generated from
the signed executable bytes, so the checksum matches the artifact that is published.

For local signing, run `pwsh worker/ci/new-signing-certificate.ps1`. It creates the code-signing
certificate in `CurrentUser\My`, prompts for a PFX password without echoing it, and exports the PFX
to `%LOCALAPPDATA%\AgentOrchestration\` outside the repository. Keep the PFX and password private
and never commit them. `worker/ci/build.ps1` automatically selects the single matching certificate;
with multiple matches, use `-SignerThumbprint <thumbprint>`.

CI release builds for `worker-v*` tags require `WORKER_SIGNING_PFX_BASE64` (single-line Base64 of
the PFX) and `WORKER_SIGNING_PFX_PASSWORD`. Add both as GitHub Actions repository secrets and as
masked, hidden, protected GitLab CI/CD variables, and protect the `worker-v*` tags. Base64-encode the
PFX locally without committing or printing it. The Windows release build fails if either variable
is missing or signing/verification fails; non-release branch and pull-request builds may remain
unsigned. Secret provisioning is a manual maintainer step and is not done by this repository change.

The signing and release workflows do not upload binaries to Microsoft or submit them for review.

#### Windows security checks

Signing establishes the selected certificate identity only; it does not make a self-signed
certificate publicly trusted, create SmartScreen reputation, or guarantee a clean antivirus verdict.
A SmartScreen “unrecognized app” warning is separate from a Defender Antivirus detection
([Microsoft developer guidance](https://learn.microsoft.com/en-us/defender-xdr/developer-faq)).

If Defender detects a worker, keep the threat name, file SHA-256 and Defender intelligence version.
Update security intelligence normally before changing or rebuilding the program. On 2026-11-06,
the unchanged release with SHA-256
`7d596083a81072989f5a7179398d5de5f42f5181e5698d038268107856faa30e`
was detected as `Trojan:Win32/Bearfoos.A!ml` with intelligence `1.463.156.0`, then scanned clean
with `1.463.163.0`. This is a result for that artifact and machine, not a guarantee for future builds.

For an explicit file check, run the installed Defender platform's `MpCmdRun.exe` with
`-Scan -ScanType 3 -File <absolute Windows file path> -DisableRemediation`.
Use a native backslash path. For this custom scan, `-DisableRemediation` ignores file exclusions
and reports detections in the console without quarantining the file; it does not turn off
real-time protection. Require both a successful scan and “found no threats” in its output.

A file scan alone does not verify runtime behavior: also exercise the downloaded worker's
opt-in install, Scheduled Task startup, program execution, update, restart and uninstall, then
check for new Defender detection events (Operational log event 1116). Keep protection enabled;
do not add exclusions to make the check pass.

If detection persists with current intelligence, preserve the artifact details and consult
Microsoft's [software-developer false-positive process](https://learn.microsoft.com/en-us/defender-xdr/submission-guide).
The worker signing and release pipeline does not submit or upload binaries to Microsoft; any such
submission is outside this workflow and would require a separate explicit decision. Neither changing
languages nor signing alone is a verified remedy for a particular detection.

### Why the PC needs no open port: the relay

The coordinator calls the PC (submit a job, poll it, cancel it, read its health), so a directly
reachable PC needs an inbound port and, on Windows, an administrator-created firewall rule. A PC
registered with the install command is reached the other way round instead:

```
coordinator code  ->  relay (127.0.0.1:8097)  <-  long poll  <-  connector on the PC  ->  execution service (127.0.0.1)
```

- The execution service on the PC listens on `127.0.0.1` only. A **connector**
  (inside `agent-worker run`) holds an outbound long poll
  (`GET /relay/<uuid>/next?wait=25`) to this server's board, which passes `/install/*` and
  `/relay/*` through to the relay service. Both skip the board login: they authenticate with the
  install code or the PC's own token.
- A coordinator call to `http://127.0.0.1:8097/w/<id>/...` (the PC's registry URL) is queued, the
  connector collects it, makes it against the local service and sends the answer back. Bodies
  stream in both directions and are never buffered (workspace transfers reach 190 MB), and the
  `X-Flow-Gate-ID` and `X-Flow-Settings-Revision` headers are forwarded.
- The PC pushes its `/health` answer every 5 seconds; the relay serves it for up to 15 seconds, so
  the Fleet tab and placement read health without a round trip per PC.
- A PC that has not polled for 40 seconds is offline. A call to an offline PC, or one nobody
  collects within 30 seconds, is answered by dropping the connection, which the coordinator
  already treats as "worker offline" (the step waits visibly and resumes when the PC returns).
- Job polls through the relay are 1 second apart instead of 0.2 seconds. Sizing: idle PCs cost one
  held request each and about 0.04 reconnects a second; a few hundred PCs are fine on one relay
  process.

Install records live in `FLOW_STATE_DIR/installs/` (git-ignored). The relay runs as its own
process under the flow host (`FLOW_RELAY_SERVICE=0` turns it off, `FLOW_RELAY_PORT` sets the port,
`FLOW_RELAY_BIND` the interface). The board container reaches it through `FLOW_RELAY_URL`
(default `http://host.docker.internal:8097`); `FLOW_RELAY_LOCAL_URL` is the address coordinators
use (default `http://127.0.0.1:<port>`).

**Security.** The plain `http://` install link and relay traffic cross your network as the board
does: use an `https://` address (for example a Tailscale Funnel or a reverse proxy) outside a
trusted private network. The form warns about plain http addresses outside private ranges. A wrong
install code gets one generic 404 after a short delay and is rate limited per source address. The
PC's token is compared in constant time on both sides of the relay.

### Advanced: register a PC the server can reach directly

For a PC that already accepts connections from the coordinator, **Register by URL (advanced)**
keeps the earlier flow: choose engines and operating system, enter the endpoint
(`http(s)://<pc host>:8096`) and the name of the environment variable that holds its token
(default `FLOW_WORKER_TOKEN_<ID>`), choose pools and tags, and set the limits. The board never
asks for the token itself. Leave the endpoint blank to save the PC as **awaiting connection**.
The form lists the manual setup steps (agents environment from a wheelhouse and npm mirror,
protected token file, service start). On that PC:

```powershell
$env:FLOW_WORKER_ID = 'build-pc'          # must equal the registered worker ID
$env:FLOW_WORKER_BIND = '0.0.0.0'
$env:FLOW_WORKER_PORT = '8096'
$env:FLOW_WORKER_SLOTS = '2'              # per-process cap: keep it at least the fleet slot count
$env:FLOW_WORKER_TOKEN = (Get-Content '<protected token file>' -TotalCount 1).Trim()
agents/.venv/Scripts/python.exe -u agents/flow_execution_worker.py
```

On Linux use `agents/.venv/bin/python` and `export`. Generate the token on the coordinator
(`python -c "import secrets; print(secrets.token_urlsafe(32))"`), store it as `NAME=value` in the
coordinator's ignored `workers.local.env` (or the flow host's environment), and copy it to a file
on the PC that only the service account can read. The service refuses a network bind without a
token. It can execute commands with that PC's account: allow inbound TCP 8096 only from the
coordinator, over a private network or HTTPS termination. No native engine credentials are needed
on execution PCs. Agent credentials, Confluence tokens and source file paths belong on the PC that
runs the step. `FLOW_WORKER_POOL` and `FLOW_WORKER_TAGS` on the PC are legacy and informational
only: the registry owns pools, tags and limits.

### After a PC connects

The coordinator checks that `/health` reports the registered ID (otherwise the PC is shown as an
identity mismatch and nothing is placed on it), then pushes the registry's slots and CPU/RAM limits
to its capacity gate. The fleet tab shows each PC's state (online, awaiting connection,
credentials unavailable, unauthorized, identity mismatch or unreachable), live CPU and RAM, slot
use, per-engine status, pools, tags, limits and their sync state, and the detected agents and
commands with their last check time. The board receives only this sanitized view, never endpoints,
token variable names or tokens.

A hand-edited `workers.local.yaml` that changes limits without bumping `settings_revision` is
refused by the gate as stale and the PC waits with `gate_unavailable`; edit through the Fleet tab,
which bumps the revision.

To let a registered PC serve another engine, edit it and add the engine. Registering the same ID
again is refused with a pointer to the existing entry, so a PC is never registered twice.

### Per-engine registration

Each selected engine has a PC-native worker except Trigger.dev, which continues to use the shared
Fleet relay bridge. Engine-native work still shares the same per-PC capacity gate as relay work:
engine assignment alone does not grant admission.

| Engine | Coordinator side | Registered PC | Important limitation |
|---|---|---|---|
| Hatchet | Submits compatible work with the Fleet placement and execution context. | A Hatchet SDK worker uses a dedicated per-PC worker-capable token and executes compatible routed work. | The PC needs the configured gRPC endpoint reachable with its TLS strategy; use a per-PC credential, never the Board-global token. |
| Prefect | Schedules compatible runs onto the configured process work pool and queue. | A process worker creates the pool if needed, reuses it idempotently, and polls its configured queue. | The configured Prefect API URL must be reachable from the PC; coordinator-internal URLs may not be. |
| Trigger.dev | Local development worker may route tasks through the Fleet bridge. | Shared Fleet relay bridge only; deployed workers remain isolated containers. | No per-PC Trigger.dev worker is advertised. |

Only compatible work routed to that PC executes in its native Hatchet or Prefect worker. A worker's
`engines` selection limits eligible engines. Trigger.dev's service route remains relay-mediated.

Admin settings provide Hatchet REST, worker gRPC host/port and TLS strategy, plus the Prefect
worker API URL. These are deployment URLs and must be reachable from the selected PC; live endpoint
reachability has not been verified against a configured Hatchet or Prefect deployment.

## Immutable flow assets and upgrade

Activation binds each YAML revision to a snapshot of the flow asset directory. Root-level flow
YAML and layout sidecars are draft controls and are excluded; helper files and nested files are
included. Old runs keep their original snapshot even when draft files change. If only assets
change, activation refuses to silently reuse the old snapshot: edit the flow YAML (for example,
update its description) to create a new revision before activating. Assets are limited by the
existing workspace transfer limits. Keep credentials outside the flows directory: activation
rejects hidden and common credential filenames, but filename checks cannot identify every secret.

An active revision from an older installation has no immutable asset snapshot. Its historical
assets cannot be reconstructed, so updated workers refuse to run it until an operator reactivates
the flow, explicitly binding its current assets. Existing queued Trigger.dev tasks without an
asset reference also fail safely; start a new run after activation. A step restart from an older
Hatchet or Prefect run whose saved definition predates asset binding is rejected; start a new
flow run because its original assets cannot be established. Activation can restart workers
and interrupt work; use the board preview before applying it. No activation is performed by this
upgrade itself.

When `FLOW_STATE_DIR` is customized, set it to the same absolute directory for the flow host and
the separately launched `trigger dev` process. Trigger.dev uses its local Python bridge to read
the immutable snapshot; a missing or mismatched directory fails the flow rather than falling
back to mutable files.

## Registry, migration and rollback

The registry is `workers.local.yaml` on the coordinator (`FLOW_WORKERS_FILE` overrides it); token
values stay in the ignored `workers.local.env` or the flow host's environment and are never
written to the registry. [workers.example.yaml](../workers.example.yaml) shows the format. Without
a registry file the fleet is empty.

A legacy (version 1) registry keeps working as it is: its single `pool` becomes the worker's only
pool membership, and IDs, tags, endpoints and `token_env` references are kept. Flow and step
selectors keep their meaning; `pool` matches any of a worker's pools. The file is rewritten as
version 2 (with `pools`, `engines`, `slots`, `cpu_limit`, `ram_limit` and the tag catalog) on the
first save from the fleet tab or the legacy `/workers` routes, or explicitly:

1. Stop everything that edits the registry (the flow host, or at least registry saves).
2. Copy the registry file, with its permissions, to a protected folder outside the repository.
   `workers.local.env` is never rewritten by migration; keep it as it is.
3. Start the flow host and call `POST /workers/migrate` on it (with `Authorization: Bearer
   <FLOW_HOST_TOKEN>` when that token is set). It answers `{migrated: true}` and writes version 2
   through a temporary file and an atomic replace, so an interruption leaves the original file.
   Running it again answers `{migrated: false}` and changes nothing.
4. In the fleet tab, check the IDs, pools, tags and that each PC with a token still shows its
   connection as configured and comes online.

To roll back, stop the registry editors again, copy the backup into the registry's folder under a
temporary name with the same protections, and atomically replace the registry with it. Restore
the backup before running an older version of this repository: older versions read only the
legacy `pool` field. Edits made after the backup are lost, so note them first. The last known
capability results of offline PCs are kept in `<registry>.inventory.json`; it holds no secrets and
can be deleted at any time.

## Choosing workers in the board

**New card.** The form asks four things, in order:

1. **What runs**: an agent, a program or a flow, the active flows shown as cards.
2. **Input**: a prompt, a command or the flow's inputs (the first text input is a paragraph; a flow
   with no inputs gets one paragraph that its steps read as `{{ input.text }}`), plus optional
   attachments, described in [Attaching files, repositories and Confluence](#attaching-files-repositories-and-confluence).
3. **Where it runs**: required tags (a worker needs all of them) and worker pools (**All pools**, or
   any number of pools, of which a worker needs one). The form says how many workers match while you
   choose. **More placement options** chooses one worker or, for a flow, workers per step.
4. **When**: right now or later, and an optional repeat. See [Schedules](#schedules).

**Starting a flow.** The pools and tags are the flow's default, and
**Choose workers for individual steps** overrides placement per step. A step's own worker ID
chooses that worker regardless of the default pool; a step pool replaces the default pool; step
tags replace the default's tags and keep its pools. A default chosen at launch replaces the flow's
default worker, and a step chosen at launch replaces that step's own setting; otherwise the flow
definition's default and step settings apply as before. While you choose, the dialog asks the flow host
(`POST /api/launch/validate`, with the selected backend) where each step can run and shows, per step:

- **Ready**: the workers that can start it now.
- **Will wait**: a possible match is offline, busy or not freshly checked; the run starts and the
  step waits for it (see [waiting reasons](#waiting-reasons-and-states)).
- **Blocked**: no registered worker can run it, with the reason and **How to fix**. **Start flow**
  is disabled, and the board refuses the launch as well. The flow itself stays saved.

Under each step every registered worker is listed as Compatible, Might match (waiting) or Not
compatible, with the reasons, and the required agent or command with its last detected status and
check time (for an offline PC, its last known result, marked as such).

**Agent and program cards.** **Where it runs** places the card on pools, tags or one worker, on
Hatchet and Prefect. It is disabled, with the reason, on Trigger.dev (cards run on the coordinator
there) and when **Advanced** has a workspace or resume ID: a placed card runs in a new workspace on
that PC. The same compatibility panel is shown, and a blocked card cannot be created.
A program card checks the executable it can read from the command. A pipeline or a variable is not
checked in advance and fails on the worker if the program is missing. Its workspace stays on the PC.
Agent cards need the agent on that PC: on the `agent-worker`, `agent-worker agents install` adds the
adapters (it needs Node.js) and the worker reports what it can run in its capabilities.
With a blank workspace and no selection, new Hatchet and Prefect cards check all registered workers and run on a compatible one. Cards using an existing workspace or resume ID run locally as before.
Python execution feeds program input while reading stdout and stderr, so a program can stream
output without reading its input. Closing stdin does not override the program's actual exit
status; the default returned stdout remains limited to its last 40 lines.
Execution bridges apply backpressure to their JSONL events and drain the final frame before
exiting, preserving complete frames even when a program produces logs faster than they are read.

**Editing a flow (Flows).** Each step's form shows **Where this step can run** for the unsaved
draft, placed the way **New card** starts it, and where its selection comes from (its own worker
setting or the default in Flow settings). The Steps list shows Ready, Waits or Blocked per step,
and Flow settings summarizes all steps. Saving is never blocked: a blocked step says "You can save
this draft; launch is blocked until this is resolved". Program steps have an **Executable
(requires_command)** field. Leave it blank when the executable is the first word of a simple
command; when it cannot be inferred (pipes, variables, scripts) the field is marked required and
launch stays blocked until it is filled in.

**While it runs.** The engine shows a placed card or step as running while it waits for a worker:
the wait happens inside the engine task, which occupies one engine execution slot meanwhile and
counts toward the step's `timeout_minutes`. This is an unavoidable constraint of the shared-service
fallback (see [Placement, waiting and cancellation](#placement-waiting-and-cancellation)). The card
drawer's **Fleet placement** section polls the execution records every 2 seconds while the drawer
is open and shows each step's state and reason; the graph labels a waiting step "waiting for a
worker" (or "intervention needed"), and its step panel explains it.

**Restarting a step.** A finished step's node panel can choose a new execution worker; the choice
is checked like a launch (a confirmed mismatch is refused, an offline or busy match is accepted and
waits). Descendants retain their own selections and restart through the engine dependency
mechanism. Hatchet replays its native DAG; the Prefect/Trigger extension creates a new native run
and reuses unaffected results. Clearing a restart override returns to the flow's selection.

### Waiting reasons and states

| `waiting_reason` | Shown as |
|---|---|
| `offline` | a matching worker is offline (or awaiting connection) |
| `credentials_unavailable` | the coordinator has no usable credentials for a matching worker |
| `full_slots` | every matching worker is busy (no free slot) |
| `high_cpu` / `high_ram` | CPU or RAM on the matching workers is at or above their limit |
| `gate_unavailable` | admission gate or registry settings could not be verified; check or update the worker service |
| `missing_metrics` | waiting for a complete 10-second CPU and RAM measurement |
| `cooldown` | the worker waits for a fresh 10-second measurement after its last start |
| `software_unknown` / `software_stale` | the required software has not been checked, or was last checked over a day ago; it is probed |
| `software_missing` | the software was missing on the chosen worker at admission; another one is sought |
| `awaiting_authorization` | the worker admitted the job and waits for the coordinator to confirm the start |
| `coordinator_unreachable` | the worker cannot reach the coordinator |
| `intervention_needed` | no registered worker can run it now; the record carries the message and resolution |

Record states: `queued` (being placed, or queued on a worker), `waiting`, `running`, `done`,
`failed`, `cancelled` (the board's cancel), `timed_out` (the step's `timeout_minutes` elapsed) and
`interrupted` (any other engine-side cancellation). The last three keep the last waiting reason,
so the board can say why the work never ran.

## How files move

The coordinator PC holds each run's published files in `FLOW_WORKSPACES` (by default
`%TEMP%/agent-flows` on Windows). Before starting a step it merges the completed ancestors' file
changes, then sends the complete input tree to the chosen service as JSON: relative paths,
base64-encoded file bytes and permission bits. The service restores it into a new job folder.
After successful execution the service sends its complete output tree back. The coordinator
records that step's changed files and deletions, and downstream steps receive a newly merged tree.

This is coordinator-mediated copying over HTTP/HTTPS, according to the registry URL. Non-loopback
worker services require a bearer token; the default loopback service may run without one. Workers
do not copy directly to one another or mount a common folder. Files become available
to dependents only when the producing step succeeds; edits are not streamed while it runs. The
network currently carries full snapshots rather than binary diffs or compressed archives. The
coordinator's saved publications are deltas. Parallel branches changing one path differently
produce an explicit conflict; identical changes are allowed, and later dependent edits win.

## Attaching files, repositories and Confluence

**New card** can attach sources to one run of any agent, program or flow. Unlike `environment` below,
this is not part of the flow's definition and nobody has to review it: what can't be prepared fails
the run with its error.

| Source | Where it lands in the workspace | How it gets there |
|---|---|---|
| Files | `context/files/<name>` | Uploaded through the board to the flow host, kept in the coordinators' shared `FLOW_WORKSPACES` volume |
| GitHub, GitLab or any git repository | `repos/<name>` | Cloned on a worker with its credential helper or SSH, shallow unless the ref is a commit |
| Confluence page tree | `context/confluence/<page id>` | Exported on a worker by the pinned exporter, with `CONFLUENCE_TOKEN` and `CONFLUENCE_EMAIL` when set there. An `agent-worker` needs no Python: it fetches a runtime from the server on first use, which needs `dist/worker/confluence-runtime-<os>.tar.gz` there (from a release, or `worker/ci/build-confluence-runtime.py`) |

Sources are prepared once per run, on a worker the run's selection allows, and every step gets the same
copy, so parallel steps don't conflict where they join. An agent's prompt gets a note listing them.
Everything attached must fit the transfer limit of **64 MiB and 10,000 files**.

Uploads the run has not used are removed after 7 days; a schedule keeps the ones it needs.

## Schedules

**When** in New card stores a card that starts later or repeats. The record is the card's request plus
its time and five-field cron, in `FLOW_STATE_DIR/schedules.json` on the flow host; the board checks
every 10 seconds and starts what is due through the same checks as a card started by hand. A schedule
therefore behaves the same on every engine, but the engine does not know about it until it starts.

Schedules show in the board's **Scheduled** column with **Run now**, **Pause** and **Delete**.

- Repeats follow the time zone of the browser that created them, across daylight saving changes.
- **Right now** with a repeat starts one run immediately, then follows the repeat.
- **If the previous run is still active** chooses what a repeat does then. **Skip this run** is the
  default, and the card says when it skipped: an agent waiting for a human would otherwise collect a
  new run each time. **Start another run** lets runs overlap. **Run now** starts one regardless.
- A start that fails is recorded on the card; a repeat tries again at its next time.
- Runs missed while the board was down are not made up: the schedule starts once and moves on.

Configure context in the existing **Flows** YAML editor. Files are source paths on the setup PC,
including directories; to upload a file for one run, attach it in **New card**
([Attaching files, repositories and Confluence](#attaching-files-repositories-and-confluence)). Git uses that PC's credential helper
or SSH, with interactive terminal prompting disabled so failures appear in setup chat. HTTP URLs
must not contain credentials. Confluence imports use
[Spenhouet's Confluence Markdown Exporter](https://github.com/Spenhouet/confluence-markdown-exporter),
pinned to **5.6.0** in `agents/requirements.txt`. Python setup workers install that requirements
file. Rust `agent-worker` PCs fetch the bundled CPython/exporter runtime from the server on first
use; no system Python is needed. Build both OS archives with
`python worker/ci/build-confluence-runtime.py --os windows` and `--os linux` (the build Python needs
pip), or fetch release assets into the server's `dist/worker/`. Linux Confluence imports require
glibc 2.26 or newer. An offline PC can use `AGENT_WORKER_CONFLUENCE_RUNTIME` with an archive or
unpacked runtime directory. Public sites work anonymously when credential fields are omitted.
Each source runs in an isolated exporter process; credentials/configuration remain outside the
transferable workspace.

The default imports the root and all descendants, preserving Markdown formatting and downloading
referenced attachments. Each page is named `<page-id>.md`; `index.json` maps IDs to titles,
versions, paths and attachment versions. Root-relative links with exported page IDs are rewritten
to local Markdown files; other root-relative links become absolute Confluence URLs. `attachments/`
contains referenced files. The exporter lockfile and `confluence-export.json`
record completion and file hashes. Missing/modified files, failed pages or attachments, and a
changed remote page tree or page/attachment version block setup completion and require re-import.
A failed refresh preserves the previous complete import. `include_descendants: false` limits the
import to one page; `attachments: all` downloads every attachment, while `disabled` skips downloads.
External linked pages are not crawled.

To reproduce the public-site check without credentials:

```powershell
agents/.venv/Scripts/python.exe -u agents/confluence_smoke_test.py
```

It imports small public Apache Tika, Atlassian and Shibboleth roots, including a six-page Tika
subtree, into ignored `agents/runtime/confluence-public`, then validates page completeness and
content hashes. Results are recorded in `verification.json`. See the
[verification record](superpowers/2026-11-03-confluence-markdown-verification.md).

The same live imports, plus a public-page transfer between two local workers, are part of the
automated suite. Run `agents/.venv/Scripts/python.exe -m unittest discover -s agents/integration_tests -v`.
The [Tests workflow](../.github/workflows/tests.yml) runs them on pushes, pull requests and daily on
the default branch. Separate jobs start disposable Hatchet and Prefect stacks and test a real
public-page import, worker transfer and native step restart. Fixture tests run separately so
public-site failures are clear; Trigger.dev native-engine smoke remains a local-stack test.

The runtime expands `environment` into a real native `setup_environment` agent node before all
root steps. It attempts each source, shows preparation errors, and opens the selected agent for
interactive repairs. It always waits for **Mark done**. Validation checks git origin/revision,
copied content and the complete Confluence Markdown export before releasing dependencies. Missing or
partial sources keep setup open. The demo agent is explicitly simulated and cannot repair files.

Each step gets an isolated workspace containing its ancestors' file changes, even on another PC.
Flow scripts referenced with `{flow_dir}` travel with the job, captured once per run and retained
for selective restart. Later sequential edits supersede
earlier edits; differing edits/deletions on parallel branches cause a merge error before downstream
execution. Identical parallel edits are allowed. Unrelated branches do not see each other's files.
Transfers preserve executable bits, reject symlinks, case collisions and unsafe paths, and are
limited to **64 MiB and 10,000 files** per tree (including repository `.git`). Large contexts need
smaller clones or a future external artifact store. Steps must put durable outputs in their
workspace; worker-local absolute paths are not portable artifacts.

Cancelled or superseded jobs cannot publish new results. Remote jobs expire after 45 seconds
without coordinator polling, including when an engine kills the coordinator process abruptly.
Finished service workspaces expire after five minutes without polling. Canonical publications
remain in `FLOW_WORKSPACES` on the coordinator PC for selective restart.

## Superseded historical feasibility probes (2026-11-04)

The following probes describe an earlier design investigation, not the current routing contract.
They remain relevant risk evidence but are superseded by the per-PC Hatchet/Prefect worker design
above; they do not establish that today's implementation works or fails.

The installed Hatchet SDK was 1.44.0 and the disposable Compose stack used server image v0.114.2.
Run-level required station selectors did not compose reliably with task selectors; separate probes
also observed task selectors placing distinct steps correctly, a run-level selector overriding
them, and a run-level desired worker ID not being honored. The SDK exposed pause but no in-place

queued cancellation probe did not execute after an eligible worker joined. An eight-minute task
scheduling timeout did not run within 90 seconds after an eligible worker joined following a
310-second wait; the engine logged a slot-replenishment timeout of undetermined cause. These were
limited probes, not complete cancellation, restart or timeout validation.

Prefect `serve()` and Trigger.dev local development were previously configured around coordinator
execution plus relay dispatch. Those historical deployment observations do not describe the new
Prefect process worker route. Trigger.dev remains a shared Fleet relay bridge; deployed workers
remain isolated containers, with no per-PC native Trigger worker.

Local integration tests exercise native dispatch against the Python worker service and the real Rust
worker binary: engine/nonce/run binding, one local execution with returned output/files, cancellation
before a late scheduler callback, and capacity-revision fencing. They do not connect to a live
Hatchet or Prefect server, and do not validate a physical multi-PC deployment.

Not verified here: live per-PC Hatchet gRPC/TLS or Prefect API reachability, endpoint failure

## Placement, waiting and cancellation

A step placed by the fleet needs a worker in its selected pool (if any) with every required tag
(or the selected worker ID), plus its software: the agent of an agent step, or the program's
`requires_command`, otherwise the first executable inferred from `run`. A leading shell builtin
such as `echo` needs no executable. A program whose executable cannot be inferred safely (pipes,
variable executables) must declare `requires_command` before launch.

Launch is blocked only when no registered worker can satisfy a step: a selection mismatch or a
fresh `absent` capability result on every candidate. The error names the mismatch and how to
resolve it; drafts can still be saved. If a potentially matching worker is offline, awaiting
connection, has no usable credentials, has unknown or stale (older than one day) capability
results, no free slot, high CPU or RAM, or missing metrics, the run launches and the step waits.
Its execution record (`/execution/<run>`) shows `state: waiting`, a `waiting_reason` and the
per-worker reasons; it never contains endpoints or credentials. Missing or unchecked software is
probed on demand, at most every 15 seconds per worker while waiting. If the software disappears
after launch, the worker rejects the job before it starts and the step waits for another suitable
worker; when no registered worker can satisfy it, the reason becomes `intervention_needed` with a
resolution, and the step resumes automatically once the fleet or software is repaired.

The native local-service and Rust-worker integration tests verify dispatch authorization, exact
engine/nonce/run checks, single local execution and result ownership, cancellation before a late
callback, and fencing after capacity settings change. They do not exercise real Hatchet or Prefect
queueing, connectivity loss, engine-side retry/restart, or scheduling timeouts. Do not infer
indefinite waiting or successful engine-side cancellation from the 2026-11-04 probes. Until live
engine tests confirm the contract, a disconnected or incompatible endpoint must not be described as
ready.

## Engine adapters and workspace integrity

Hatchet and Prefect selected in Fleet use per-PC native workers: the Hatchet SDK worker uses a
dedicated PC token, and Prefect uses a process worker on a reused or created work pool/queue.
Compatible routed work executes on that PC after admission through the shared per-PC capacity
gate. Trigger.dev remains relay-mediated; deployed Trigger.dev workers are isolated containers,
not per-PC native workers.

The relay bridge remains available for Trigger.dev and any explicitly routed shared-service work.
Its execution record shows `engine`, the actual execution `worker`, `state` and `waiting_reason`.
For a flow step, the record is under `/execution/<run>` (`steps.<step>`); for a card, under
`steps.card`, served at `GET /api/cards/<system>/<run>/execution`. Records must not expose engine
tokens or endpoints.

The board defaults a new blank-workspace Hatchet or Prefect card to any compatible fleet worker; its requirement includes the agent. The board sends an empty `tags` selection for this default. Existing engine jobs without a `worker` selection continue to run on the engine worker. A placed card runs in a new workspace on the executing PC, as a blank-workspace card does.
A host workspace path or a resumed session (bound to its original workspace) is refused for a
placed card, both when it is created and by the worker service, rather than assumed to exist on
another PC. A card transcript keeps its event schema: the executing PC is in the record, not the
transcript. Placed cards on Trigger.dev are not supported; that board backend refuses a selection.

Native wait bounds and engine-side queue/cancellation behavior are not verified against live
Hatchet and Prefect servers. Keep the configured step timeout and engine queue timeout distinct;
do not imply that a queued native task can wait indefinitely or that cancellation immediately
stops a remote process. Trigger.dev development TTL and retry settings apply only to its bridge
mode and do not create native workers.

Revisions: each job carries the exact flow definition and the run's asset snapshot, so a worker
never reads flows or assets from its own disk, and a worker update cannot change a running job. The
first step of a run pins the definition hash, for placed and local flows alike. If the flow is
updated while an old run is in flight, an engine worker serving the new revision may still receive
the old run's remaining or parallel steps. They fail with "The flow definition has changed; start
a new flow run" before anything is placed or published, so revisions never mix. If activating
the new revision failed for an engine, that engine keeps serving the old revision and old runs
finish on it.

The coordinator owns the run workspace. Relay-dispatched jobs receive files through the
authenticated service API, within existing transfer limits, and run in a per-job directory on the
executing PC. Results are published only while the attempt's fence is current; superseded attempts
cannot publish. Parallel branches that change the same file on different PCs conflict before the
joining step. Native Hatchet/Prefect workers must preserve the same authenticated transfer,
workspace isolation, limits, conflict behavior and fencing; this end-to-end native path is not
verified here and must not assume a shared filesystem.

The registry's `slots`, `cpu_limit` and `ram_limit` are synchronized to the PC's capacity gate.
For native engine work, the gate must be the same per-PC admission authority used by relay tasks;
engine-local concurrency limits alone are insufficient. Contention across native and relay routes,
including lease cleanup, cancellation and fencing races, remains unverified. Registry updates
affect new admission only. The configured `engines` list limits which engines may place work on a
worker.

## Capability detection

Each execution service detects the supported agents (including their ACP adapters) and the
commands steps need, in its own execution environment: at startup, whenever its results are more
than a day old (checked hourly, and when the coordinator reads them, which covers a reconnect),
on **Refresh capabilities** in the fleet tab, on demand while a step waits for a command or agent
that is not freshly installed (at most every 15 seconds per worker), and once more immediately
before a job starts. Results are `installed`, `absent`, `unknown` or `error`, each with its check
time. Installed does not mean signed in: authentication readiness is reported as unknown. A result
older than a day counts as unknown, never as absent; only a fresh `absent` makes a worker not
compatible. The coordinator keeps the last known results of each PC so an offline PC still shows
when it was last checked; they are shown, never used as a verified answer.

## Capacity: CPU, RAM, slots and cooldown

Each execution service samples the whole machine every second into the PC's shared capacity store:
CPU from the OS's idle and busy counters between samples (`GetSystemTimes` on Windows,
`/proc/stat` on Linux), and RAM as physical memory in use, `(total - available) / total`, using
the OS's available-memory figure (`GlobalMemoryStatusEx` on Windows, `MemAvailable` on Linux), so
readily reclaimable cache counts as free. macOS is not sampled: a macOS PC always reports unknown
capacity and its gate never admits work.

The admitted value is a time-weighted average over the last 10 seconds of a monotonic clock. It is
unknown (waiting reason `missing_metrics`) until samples cover a full 10-second window, when the
newest sample is more than 3 seconds old (stale), and after a gap of more than 3 seconds between
samples, which restarts the window. A PC is not eligible for new work while either average is at
or above its limit (`high_cpu`, `high_ram`; default 90%). These are admission thresholds, not caps
or predictions: running jobs are never interrupted when a limit is exceeded or changed.

Admission is serialized per PC in one SQLite store shared by every service on it
(`FLOW_CAPACITY_DB`, default `%PROGRAMDATA%\agent-orchestration\capacity.db` on Windows and
`/var/tmp/agent-orchestration/capacity.db` on Linux; never a network drive). In order, a new job
waits while the PC's leases fill its slots (`full_slots`, counted across all engines), while
another admission is still starting, during the cooldown (`cooldown`: for 10 seconds after the last
confirmed start, and until a sample taken at least 10 seconds after it exists), while metrics are
unknown, and while CPU or RAM is at or above its limit. The cooldown and samples survive service
restarts and reconnects. A lease lasts 30 seconds and is renewed every 5 seconds while the job runs.

The Python execution service waits for in-flight capacity bookkeeping and termination records
during cancellation and shutdown. Cancelling a coroutine does not abandon its SQLite operation;
the service releases its connections before teardown completes.
Execution can stop while the database is locked; termination is acknowledged only after its
durable revocation is committed.

## Crash recovery and its limits

An expired lease is not reused while its work may still run: the reservation stays blocked until
the execution is known to have stopped. A reservation whose owner died before the job started is
reclaimed. A started job's reservation is reclaimed after its process tree is verified dead
(a Windows named Job in the same OS session is terminated and checked; on Linux the session or
process group must be gone) or after a verified reboot (a changed OS boot identity).

**Limitation (POSIX):** live orphan process groups on Linux and other POSIX systems are not
terminated automatically. If an execution service or its coordinator crashes while a job's process
group keeps running, that PC's reservation stays blocked (the PC shows a used slot and new work
waits with `full_slots`) until the group is verified dead or the PC reboots. Unattended POSIX crash
recovery is not supported: an operator must stop the orphaned processes, or reboot the PC. On
Windows, a Job owned by another OS session or account cannot be opened, and its reservation stays
blocked in the same way.
